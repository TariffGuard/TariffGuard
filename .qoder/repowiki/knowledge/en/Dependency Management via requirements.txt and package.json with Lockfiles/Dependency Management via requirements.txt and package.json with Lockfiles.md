## What system/approach is used

The TariffGuard platform manages third-party dependencies using two separate, language-native package managers — one per subproject:

- **Backend (Python/FastAPI)**: `pip` via a flat `backend/requirements.txt`. All runtime and test dependencies are pinned to exact versions using the `==` operator.
- **Frontend (Next.js/React)**: `npm` via `frontend/package.json` plus a committed `frontend/package-lock.json` (lockfileVersion 3). Dependencies use caret (`^`) ranges for most packages, while core framework packages (`next`, `react`, `react-dom`, `eslint-config-next`) are pinned to exact versions.

There is no monorepo-level dependency manifest; each subproject declares its own dependencies independently. No vendoring of Python or JavaScript source code exists in the repository.

## Key files and packages

- `backend/requirements.txt` — single source of truth for all backend Python packages (FastAPI, SQLAlchemy, PyMySQL, Pydantic, httpx, pandas, numpy, pytest, etc.). Every line uses an exact pin (e.g. `fastapi==0.104.1`, `sqlalchemy==2.0.23`).
- `frontend/package.json` — declares both `dependencies` and `devDependencies` for the Next.js dashboard (Next 16, React 19, Recharts, Tailwind v4, Jest, ESLint, TypeScript).
- `frontend/package-lock.json` — full deterministic lockfile generated by npm, recording every transitive dependency's resolved version and integrity hash under `node_modules` resolution from the public npm registry.
- `docker-compose.yml` — references the backend image built from `./backend` (which installs from `requirements.txt`) and mounts the frontend source directory; no private registries or custom package sources are configured here.
- `backend/Dockerfile` — installs backend deps via pip using `requirements.txt` (no custom index URL configured).

## Architecture and conventions

- **Per-subproject manifests**: The repo treats the backend and frontend as independent projects with their own dependency declarations. There is no shared workspace, pnpm workspaces, or pip-tools/pipenv/Poetry configuration.
- **Exact pins on the backend**: `requirements.txt` pins every package to an exact version (`==`). This enforces reproducible builds across environments without needing a separate lockfile.
- **Range-based + lockfile on the frontend**: `package.json` uses semver ranges (`^`) for most packages to allow patch/minor updates, while relying on `package-lock.json` to freeze the exact tree installed in CI and production. Core framework packages are pinned exactly to avoid drift between `next` and `eslint-config-next`.
- **Public registries only**: Both `pip` and `npm` resolve against the default public registries (PyPI and https://registry.npmjs.org). No `.pypirc`, `PIP_INDEX_URL`, `--index-url`, `.npmrc`, `NPM_CONFIG_REGISTRY`, or private proxy configuration was found.
- **Dockerized install**: The backend container installs dependencies at build time from `requirements.txt`; the frontend is mounted as a volume during development and built via `next build` inside the container.

## Conventions and constraints

- Backend Python dependencies must be added to `backend/requirements.txt` with an explicit `==` pin; there is no mechanism for loose versioning in the backend.
- Frontend dependencies should be declared in `frontend/package.json` under the appropriate `dependencies` or `devDependencies` section; changes must be accompanied by an updated `package-lock.json` to keep the lockfile in sync.
- No vendored copies of third-party libraries exist anywhere in the repository — all code is fetched at install/build time from public registries.
- Environment variables consumed by the backend (e.g. `ALCHEMY_KEY`, `QWEN_API_KEY`) are injected at runtime via Docker Compose environment mapping; they are not managed as package dependencies.
